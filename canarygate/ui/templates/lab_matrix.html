{{ icon("inventory") }} What the demo matrix covers

three runs answer all nine cells

Each read-BOLA run records two owner baselines, both cross-account directions and both secure-route checks. These three ordered pairs therefore cover every combination; the catalog lists them as coverage_pairs. Running a pair twice produces duplicate evidence, which the matrix counts and lists instead of hiding.

The six ordered pairs in the catalog are every request the API accepts, not the minimum set: a pair run always checks both directions, so A→B and B→A are the same two runs' checks seen from opposite ends.

{{ icon("reload") }} Reset the interaction condition

POST /api/lab-sci-resets

The interaction flaw is stateful: a rejected login leaves a legacy compatibility flag for one account, and a successful login clears it. The reset proof performs that clearing in a separate controlled execution with two fresh runners.

What the reset clearsWhat it preserves
The lab's per-account compatibility flag for the pair you select (403 → 401 → 200 → 403 is re-proven from scratch). Every stored run, matrix cell, evidence hash, report and reset proof already recorded. Nothing is deleted or rewritten.
A reset is evidence, not a cleanup: it cannot consume the primary interaction run's one-read state.
