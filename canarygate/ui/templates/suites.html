{{ icon("key") }} Authentication scenarios

POST /api/authentication-scans

Runs the eight P0 authentication checks (AUTHN-01 … AUTHN-08) for one token transcript. Inapplicable checks are reported as SKIPPED with a reason.

Titles are the backend's own scenario titles, not predicted outcomes.

{{ icon("search") }} Input and disclosure scenarios

POST /api/validation-scans

Runs the INPUT and DISC checks over recorded request/response transcripts. Signature-based disclosure detection is described as partial by the backend's own audit, and the run says so.

There is no run-level verdict in this family; per-check verdicts are the record.

{{ icon("matrix") }} Control-interaction scenarios

POST /api/interaction-scans

Two controls that each pass alone, then the combined action. The engine decides whether the weakness is interaction-induced, and can return SKIPPED or INCONCLUSIVE without pretending the test passed.

{{ icon("info") }} What these suites demonstrate

  • Read-BOLA — the decision path that turns ownership proof and private-data disclosure into a verdict, including honest non-CONFIRMED outcomes.
  • Authentication — missing, malformed, wrong-scheme, crafted-JWT and API-key probes, with the effective-identity change required before a probe can be CONFIRMED.
  • Input / disclosure — validation probes and signature-based disclosure checks, with their limits stated in the run.
  • Interaction — a weakness that exists only in the combination of two individually correct controls.
  • Every run records request counters and limits the backend applied.
