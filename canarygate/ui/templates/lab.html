{{ icon("shield") }} Read-BOLA

POST /api/lab-bola-scans

Six checks on the lab's record endpoints: owner baselines, the cross-account read on the vulnerable route, and the checked denial on the secure one. Ground truth is scored afterwards, never used to decide.

The backend answers the pair this selection names (for an asset you own, that is the owner baseline). One run also reads the same pair in the reverse direction and on the secure route, so the comparison on the run page is drawn from real checks only.

{{ icon("key") }} Control interaction

POST /api/lab-sci-scans

Deny, then a rejected login, then the identical read again. Two correct controls interact and the guard stops protecting the record. The verdict comes from the shared SCI decision engine, not from the sequence being 403 → 401 → 200.

The interaction needs two different accounts. The requester sets the lab condition and the asset must belong to the other account, whose private marker is the disclosure proof. A selection where both are the same account is refused, not simulated.

{{ icon("info") }} What the browser is allowed to do

  • The forms submit a port, an account and an asset. The account and asset are looked up in the published catalog and posted as the pair the backend declares. The browser cannot name a host, a path, a credential or an expected verdict, and the backend's request model rejects extra fields.
  • The scope, credentials and plan are built by the backend. The lab's passwords, tokens and private markers are never sent to the browser.
  • A refusal is shown as a refusal: HTTP 400 for a bad configuration, 502 when the lab is unreachable, and no evidence is stored in either case.
  • Run ids above are links to the stored evidence, the section report and the backend's own HTML report.
